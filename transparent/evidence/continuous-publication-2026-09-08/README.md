This run replaces the morning's static tail with a node-following publisher and a warm, revision-aware fleet. The service passed a continuous 20-block acceptance window after the corrections below. A final adapter rerun exposed a map/filter race in the older client pin. The library correction is committed, but the existing wallet adapter needs an accepted-anchor API migration before it can adopt the new pin.

The first activation found the retrieval DNS still pointing to the pilot. A saved Terraform plan changed only that DNS record. The pilot forwards wallet routes to the router during cached-DNS overlap. No credential or private key is in this evidence.

The first active observation exposed recent-worker OOM under revision churn. Unpinned retired runtimes are now evicted before building, and prewarm builds current revisions only. A 12-generation private canary confirmed runtime reservations remained bounded, but a subsequent real-block window exposed another lifetime bug: the server retained its startup snapshot, and one held old reader prevented collection of every newer idle snapshot. `6e0c65c` releases the startup clone and collects idle snapshots independently while preserving the latest three and any individually held readers. Its regression deliberately holds an old reader through six activations.

The corrected private canary completed 12 activations with `retired_snapshots` bounded at three after explicit collection, no restarts or OOM events, and 3.75 GiB reserved runtimes. It reused three canonical maps; this is a churn/lifetime test, not twelve newly mined blocks. Its first cold preparation exceeded the fleet helper's request timeout; the retry reused in-progress preparation. The raw log preserves that attempt. Cgroup page-cache reclaim reached the 7 GiB limit without an OOM; process RSS is recorded separately.

`initial-attempts/` preserves failed and interrupted acceptance windows, the canary harness corrections, and the pre-fix generation backlog. ## Burst latency correction

The first window after the memory fix completed eleven new blocks before it was stopped, with no HTTP errors or orphaned endpoint samples. Closely spaced blocks exposed queueing behind the prior build: maximum visibility latency was 37.24 seconds, outside the 30-second target. One pair of sequential origin reads straddled an atomic activation; the following sample agreed. This window is preserved as `initial-attempts/burst-freshness-failure.jsonl.gz` and does not count as acceptance.

`51ca6bb` reuses authenticated SSH sessions for short control and transfer calls, records command durations, and avoids reloading an unchanged router configuration only when a successful application marker agrees. A retry after an interrupted rename/reload still reloads. This reduced individual control calls from about 0.31 seconds to 0.01–0.04 seconds, but profiling showed cancellation of slower multiplexed preparation channels could still delay quorum. A controlled `sleep 3` command proved cancellation waited 2.517 seconds through the multiplex master and 0.00064 seconds on a direct connection. `08e2261` therefore uses direct connections for long preparation calls and reuse for short calls. No worker restart or memory-budget change was needed. Thirteen operations tests, including withdrawal, interrupted reload and connection selection, pass.

## Wallet scope and limitations

The actual Zakura adapter (`zakura-wallet-transparent` in `valargroup/wallet-libraries`, pinned PIR `5758ffd`) is exercised over both public HTTPS origins: fresh recovery with a fixed unused synthetic seed, a revision-bound recent-tail private query, and an archive private query. The tested wallet checkout had pre-existing uncommitted integration changes at HEAD `4d953514`; `wallet-source.json` records hashes of the relevant crate files and lockfile, and this task did not edit that checkout. Fresh recovery completed through 3,476,342 in 3.777 seconds, with a 2.140-second repeat. The tail directory-row query took 0.980 seconds (19,435 B setup, 128,008 B upload, 5,136 B response); the archive row took 1.233 seconds (19,436 B setup, 258,056 B upload, 5,136 B response). These are adapter-reported protocol bytes, excluding full TLS/HTTP overhead and filters. All three tests passed. This confirms wire compatibility and advertised coverage. It does not verify the user's payment or balance: no transaction identifier or owned script was supplied. The fresh-wallet fixture takes publication boundaries as its accepted test chain view; the separate observer checks those endpoints against the node.

A later live recovery at the existing `5758ffd` pin raced activation and failed with `shard 173 filter does not match its published digest`; the log is preserved in `initial-attempts/wallet-map-filter-race.log`. `87226c31e6e3d42b6707992e9303e85da9a044d2` fixes this in the reference library: mismatched bytes are neither cached nor matched, and a bounded refresh must produce a changed, validated map before retrying. Corrupt bytes with an unchanged map still fail after one refresh. The client/store/server suite passed **146 tests across 22 targets**, strict Clippy passed, and both dedicated race/corruption tests passed with exact ledger and byte-accounting assertions.

An isolated copy of the existing wallet checkout was then pinned to `87226c3`. **That build failed before any live requests** because the adapter still implements the earlier store API: `rollback_above` takes a height rather than an accepted `Anchor`; `sync_into` lacks the target anchor; persisted coverage lacks `source_anchor`; pending pages lack `target_anchor` and `validated_events`; completion mapping lacks `PublicationBehind` and `UnresolvedSpends`. `initial-attempts/wallet-updated-pin-recovery.log` and the attempted manifest patch preserve this finding. The pin-only patch is **not a ready migration**. The shared wallet checkout was not edited. Migrating its accepted-anchor persistence and rerunning its recovery suites is tracked in [remaining work](../../docs/remaining-work.md).

The earlier fixed-publication accepted-anchor regression and fleet saturation gates remain separate. This run is not a capacity benchmark, a mobile-device test, an archive redundancy rehearsal or a production deep-reorg injection. The topology still has disjoint archive owners and one router. During the worker repair, publication preparation was paused while ingestion and reorg withdrawal remained active; archive binary restarts temporarily made those owners unavailable.
