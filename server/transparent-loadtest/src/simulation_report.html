TRANSPARENT PIR · RECOVERY SIMULATION

Load and client resources

One-second samples. CPU is shown in cores consumed; RSS sums the supervisor and current wallet workers. Request rates include retries. Payload upload is submitted bytes, excluding HTTP/TLS overhead.

Wallet profiles

Latency percentiles include exact recoveries only. Fewer than 100 exact completions are marked sparse. Failures and incomplete work remain in outcome counts.

Wallet timelines

Bars run from actual worker start to terminal outcome. Start offset reveals scheduling skew. Expand stages to see HTTP activity windows; overlapping windows are not a decomposition of total time.

Per-wallet aggregates

Grouped by sample wallet across all recoveries, including sustained replacements. HTTP time sums request durations; it is not wall-clock recovery time. Exact latency excludes unsuccessful recoveries.

Server APM

Each named target is scraped independently. All traffic reaching that worker contributes, including unrelated clients. Queue depth includes waiting and running requests. Cache reservations and process RSS measure different things. Latency quantiles come from interval histogram deltas, never averaged across workers.

Payload accounting

Provenance and limits

Every measured recovery uses an independent store seeded with prior ledger events when its window starts after the publication start. Filter/setup caches start cold. Preparation reports are separate; preparation can warm server caches. The runner does not reset server caches. No socket-level, TLS, or mobile-network measurements are inferred. A client timeout may leave an already admitted server evaluation finishing in the background. Missing metrics are unavailable, never zero.
